# boardgame-design

桌游设计不是一个线性流程，而是**迭代引擎**。每个阶段都是「AI 产出 → 人评审 → 打回重做」的循环。

## 设计流程总览

```
阶段 ① 概念定义  ──→  阶段 ② 核心循环  ──→  阶段 ③ MVP 构建
    ↑                     ↑                      ↑
    ↓                     ↓                      ↓
    评审打回               评审打回                评审打回
                                                      ↓
阶段 ⑥ 规则书定稿  ←──  阶段 ⑤ 人类测试  ←──  阶段 ④ 项目自定义
    ↑
    ↓
    评审打回
```

每个阶段 AI 产出指定内容，你根据评审标准判断是否通过。不通过则反馈问题，AI 迭代修改。

> **注意**：阶段切换由人通过特定指令（如"推进进入阶段④"）触发。AI 在完成当前任务后停机等待指令。

## 通用规则

- **逐任务推进**：每次只执行一个细分任务，执行完后完全停止，等待下一次指令
- **推进与对话区分**：切换任务时需要说"推进"；直接给修改意见时不需要
- **唯一方案**：除非另有要求，聚焦于一个主线方案
- **阶段切换由人触发**：AI 完成当前任务后停机等待，由人发出"推进进入阶段④"等指令切换到下一阶段

## AI 能力边界

| AI 能做                    | AI 不能做（需要人）        |
| -------------------------- | -------------------------- |
| 产出多个方案选项           | 决定"这个 idea 好不好玩"   |
| 引用方法论对比优劣         | 判断"这个机制爽不爽"       |
| 检查规则逻辑漏洞/边界条件  | 真实玩家测试体验           |
| 术语一致性检查             | 验证规则书"路人能不能看懂" |
| 概率计算与数值验证         | 感受游戏的节奏和氛围       |
| 生成结构化规则书草稿       | 动手制作物理原型           |
| AIvAI 跑通流程验证无死循环 | —                          |

## 阶段 ①：概念定义

**AI 产出**：「概念卡片」，包含以下内容：

1. **一句话 Hook**（30 秒 Hook）
   - 格式：玩家扮演「身份」，通过「核心动作」达成「目标」，核心阻力是「冲突/张力」
   - 检验：念给非桌游玩家的朋友听，30 秒内对方能否产生期待

2. **锁定参数**
   - 玩家人数（精确数字，如 2 人 / 4 人 / 可变人数范围）
   - 单局时长（精确到分钟，如 30-45 分钟）
   - 复杂度层级：轻量 / 中策 / 重策
   - 核心机制类型（参考主流玩法类型）

3. **主流玩法类型速查**（极简列举，用于定位你的游戏属于哪一类）

   ```
   卡牌驱动   | 骰子驱动   | 工人放置  | 区域控制
   引擎构筑   | 牌库构筑   | 成套收集  | 拍卖竞标
   网格移动   | 路径规划   | 资源管理  | 合作/半合作
   推理/ bluff | 记忆匹配   | 纸笔书写  | 实时/限时
   秘密身份   | 谈判交易   | 板块拼接  | 骰子放置
   故事驱动   | 推理解谜   | 技巧/动作 | 抽象棋类
   ```

   AI 应从中标记 1-3 个最接近的类型，并说明理由。

4. **模糊假设清单**
   - 列出当前设计中的所有未确定假设，例如"假设玩家 2 人时体验与 4 人一致"、"假设每回合行动选择在 3 个以内"等
   - 这些假设将在后续阶段逐步验证或修正

**评审标准**（人判断）：

- [ ] 这个 hook 听起来好玩吗？
- [ ] 参数设定是否合理（时长/复杂度是否匹配）？
- [ ] 你对机制类型的选择认可吗？
- [ ] 模糊假设清单是否有遗漏？

**通过**→进入阶段 ②。**不通过**→反馈具体问题，AI 重产出。

## 阶段 ②：核心循环设计

**前置条件**：阶段 ① 的概念卡片已通过评审。

**AI 产出**：核心循环方案

1. **核心循环定义**
   - 用「接收 → 选择 → 解决 → 回应 → 传递」或自定义格式描述玩家的最小重复决策单元
   - 识别唯一的"最难决策点"（HDP）——玩家在每回合中最烧脑的那个选择
   - 诊断 HDP 的信息来源：这个决策依赖哪些可见信息？是否有足够的推理依据？

   > 参考：`docs/core-loop.md` 查看核心循环设计方法论

2. **回合结构方案**
   - 如果游戏有回合概念，给出推荐的回合结构方案，包含：
     - 回合顺序类型（固定顺序 / 渐进式传递 / 竞标顺序 / 同时选择 等）
     - 先手/顺序优势的补偿方案（如有）
     - 回合流程的"3-2-1"简化检查

   > 参考：`docs/turn-order.md` 查看 10 种回合结构变体及选择框架

3. **胜利条件设计**
   - 终局触发条件（达成目标 / 回合数耗尽 / 牌库清空 等）
   - 胜负判定方式（得分最高 / 首个达成目标 / 存活到最后 等）
   - 胜利条件与核心循环的关系：玩家在做核心循环时，每一步是否都在"靠近胜利"？

4. **备选方案**
   - 如果有替代的核心循环设计思路，一并列出，供你选择

**评审标准**（人判断）：

- [ ] 核心循环听上去有趣吗？
- [ ] 最难决策点是否真的有策略深度？
- [ ] 回合结构方案是否合适？
- [ ] 胜利条件是否清晰且有驱动力？

**通过**→进入阶段 ③。**不通过**→反馈具体问题，AI 迭代。

## 阶段 ③：MVP 构建与审查

**前置条件**：阶段 ② 的核心循环方案已通过评审。

### ③-A：构件产出

按顺序逐个产出设计文档。每产出 1 个就初步确认，避免多文档耦合导致的同步问题。

**产出原则**：从最核心的机制开始向外扩展，优先级递减。

1. **核心机制的物理载体**（最优先）
   - 定义玩家每回合做什么、怎么赢、有哪些基本操作
   - 这是玩家不靠任何特殊能力也能玩到的东西，是所有其他机制的基础
   - 确保：术语一致、没有未定义的边界条件
   - 参考：`docs/rulebook.md` 查看规则书写规范

2. **玩家差异的来源**
   - 如果玩家之间存在不对称性（不同角色、阵营、初始资源等），在这里定义
   - 确保差异化设计不破坏核心机制的完整性
   - 差异应该是"选择带来的多样性"，而非"规则不公"

3. **环境与交互的载体**
   - 玩家在哪里做决策？版图、地点、公共区域等（如有）
   - 资源如何分布、如何消耗、如何获取
   - 如果游戏没有实体版图，这部分可以非常简略或者不存在

4. **打破常规的手段**
   - 玩家可以如何突破基础规则的限制？卡牌、事件、特殊能力等（如有）
   - 确保这些手段的效率与基础操作保持合理的比例关系
   - 如果游戏不依赖卡牌/特殊能力，这部分可以不存在

> **[数据完整性原则]**：所有设计数据只存在于各自的源文档中（规则书、角色、版图、卡牌等设计文档）。审查时直接从源文档重新计算，无需创建独立的汇总表。详见 `docs/prototype.md`。

### ③-B：系统化评审

按层次依次产出多个专项评审文档，而非一份大杂烩。

**评审文档清单**（在一次推进中依次产出以下 5 个文档）：

1. **`r01-非量化评审`**
   - 覆盖所有不涉及数据的评审内容：
     - 规则书逻辑漏洞、规则矛盾、描述歧义
     - 角色定位合理性、能力设计趣味性、阵营互动频率
     - 卡牌效果平衡性、机制是否有趣
     - 游戏节奏、回合流畅度、上手难度
     - 规则完整性：是否有未覆盖的边界情况

2. **`r02-量化基准`**
   - 第一步：检查基础操作（投入产出关系）是否一致，有矛盾的先修复
   - 第二步：建立 **0 特殊能力数值基准**：不考虑特殊能力/技能时，各阵营/路线的基础效率
     - 分析各种策略的资源投入产出比
     - 分析每种策略的执行周期（多少回合完成一次）
     - 分析理性选择下，玩家会优先选择哪些目标
     - 各情景下的预期得分/进度

   > 量化方法论参考 `docs/balance.md`

3. **`r03-设计审查`**
   - 根据 r02 的基准检查设计质量：
     - 环境系统：资源/收益梯度是否合理
     - 角色/能力：使用 `docs/balance.md` 中的收益分析框架进行成本收益分析
     - 特殊手段：效果/成本分析、是否会导致单一策略最优
     - 总结强度分布（超模/合理/偏弱）

4. **`r04-综合计算`**
   - 加入所有特殊能力、环境效果、卡牌效果后的综合结果
   - **深层漏洞检查**（以下维度必须系统检查，详见 `docs/balance.md`）：

     | 维度               | 说明                                                     |
     | ------------------ | -------------------------------------------------------- |
     | **资源耗竭曲线**   | 模拟有限资源的消耗趋势、耗竭时间点、耗竭后的游戏状态变化 |
     | **成本突变检查**   | 资源耗尽是否导致成本跳跃性变化                           |
     | **循环完整性检查** | Token/资源从产生→消耗→回收的全链路是否闭环               |
     | **交叉组合风险**   | 能力×环境×特殊手段的协同是否超出预期                     |
     | **策略收敛检查**   | 是否所有玩家都被迫涌向同一个最优策略                     |
     | **非对称补偿检查** | 弱势方是否有足够补偿                                     |

5. **`r05-修改指令`**
   - **最后一个产出**，汇总 r01~r04 的结论
   - 作用：给 AI 自己（在修改环节）用的行动清单，不是给人看的详细评审报告
   - 格式：极度精简，只包含"改什么"和"为什么改"，无背景分析或方法论引用

   ```
   ## 🔴 必须修改

   1. [文档X §Y.Z] [具体字段] 改为 [新值]
      → 原因：一句话解释

   2. [文档X §Y.Z] 重写 [具体段落]
      → 原因：逻辑矛盾

   ## 🟡 建议修改

   3. [文档X §Y.Z] [建议修改]
      → 原因：潜在风险点

   ## 🟢 可延后

   4. [文档X §Y.Z] [建议]
      → 原因：非关键
   ```

**评审标准**（人判断）：

- [ ] 初始规则草稿是否有明显的逻辑漏洞？
- [ ] 量化审查有没有发现严重失衡？
- [ ] 深层漏洞检查有没有发现问题？
- [ ] 你对 r05 的修改指令认可吗？

**迭代循环**：③-B 产出 r01~r05 → ③-C 人反馈意见 → ③-D AI 根据 r05 修改 → 回到 ③-B 新一轮评审。循环直到人决定进入下一阶段。

## 阶段 ④：项目自定义阶段

**前置条件**：阶段 ③ 的 MVP 方案已通过评审。

此阶段内容由具体项目自行定义，本 skill 不预设流程。例如：

- **AI 模拟测试**：开发游戏引擎 → 并发 AI agent 模拟 → 分析结果 → 循环修改
- **其他验证**：任何项目需要的自定义验证步骤

> 此阶段的具体流程、产出、里程碑在项目的工作流程文档中定义。

## 阶段 ⑤：人类测试

**前置条件**：阶段 ④ 完成后，设计已初步验证通过。

**人负责**：

- 制作物理原型
- 组织真实玩家测试
- 判断游戏是否有趣
- 记录测试中出现的"信号词"
- 简单的问题直接由人手动修改设计文档
- 仅在涉及大量改动（跨多个文档、大规模数值调整）时，给 AI 提出修改意见，由 AI 统一批量修改

**AI 产出**（按需调用）：

- 当人类给出明确的修改意见时，AI 统一修改涉及的批量文档
- 确保修改后的规则书与其他设计文档一致

**测试反馈循环**：

```
人测试 → 记录问题
    ↓
  简单修改？→ 人直接改 → 再测试
    ↓ 否
  涉及大量改动？→ 人给修改意见 → AI 批量修改 → 再测试
```

**评审标准**（人判断）：

- [ ] 真实玩家玩得开心吗？
- [ ] 新手能说出"下次我应该怎么做不同"（而非"全凭运气"）
- [ ] 有没有测试信号词触发？

**迭代**：循环测试→修改→测试，直到人满意。

## 阶段 ⑥：规则书定稿

**前置条件**：设计已基本稳定，测试反馈已处理完毕。

**AI 产出**：完整规则书

1. **规则书结构**
   - 按标准模板生成完整规则书
   - 结构：概述 → 组件说明 → 设置 → 核心概念 → 回合结构 → 行动详解 → 终局与计分 → 变体规则 → FAQ

2. **术语一致性检查**
   - 建立完整的术语对照表（使用 / 避免）
   - 确保全篇术语统一

3. **边界条件与 FAQ**
   - 整理所有已发现的边界条件处理方式
   - 编写 FAQ 条目（Q&A 格式）

4. **评审检查**
   - 让不是设计师的朋友读一遍规则书，标记所有困惑的地方
   - AI 根据反馈修改

   > 参考：`docs/rulebook.md` 查看规则书写完整规范

**评审标准**（人判断）：

- [ ] 规则结构清晰吗？
- [ ] 路人（非设计师）能看懂并玩起来吗？
- [ ] 所有边界条件都有定义吗？
- [ ] 术语是否一致？

**通过**→设计完成。**不通过**→反馈问题，AI 迭代修改。
