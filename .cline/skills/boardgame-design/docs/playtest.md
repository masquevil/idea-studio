# 测试方法论

## 可选：AI 驱动模拟测试

> 在制作物理原型前，可以增加一个 AI 模拟测试阶段。适用于数值复杂度较高的游戏，在投入物理原型前先通过 AI 模拟发现重大问题。

**方法框架**（具体流程在项目中进一步细化）：

1. AI 开发游戏引擎（CLI 版，支持 JSON I/O）
2. AI 开发并发测试工具，支持同时运行多个游戏实例
3. 每个测试实例调用 2-7 个 AI agent 模拟人类玩家，通过引擎进行完整对局，记录完整流程
4. AI 分析所有流程和结果，检查问题（失衡、无趣选择、死循环等），提供修改建议
5. AI 总结修改建议 → 询问人 → 人给意见 → AI 修改设计 → 再次并发测试，循环

**注意**：这个阶段是高级选项，并非每个游戏都需要。是否需要以及在项目中如何使用，由人在具体项目的工作流程中自行定义。

---

## AI 测试 vs 人测试

| 测试类型 | 谁做 | 目的 |
| --------- | ------ | ------ |
| 规则完整性审查 | AI | 检查规则中是否有逻辑漏洞、未定义的边界条件、术语不一致 |
| 数值概率验证 | AI | 计算概率分布、检查资源曲线是否合理、检测是否存在"最优解" |
| AIvAI 流程跑通 | AI | 模拟对局验证流程能否完整执行、有无死循环 |
| 规则可读性测试 | 人 + 朋友 | 非设计师的朋友读规则书能否自行上手 |
| 真实玩家测试 | 人 | 验证游戏是否有趣、玩家是否享受决策过程 |
| 盲测 | 人 + 陌生人 | 完全依赖规则书，无设计师在场，能否正常游戏 |

## 测试信号词体系

玩家在测试中不经意说出的话是最可信的反馈。以下是需要修改的明确标志：

| 信号词 | 含义 | 修改方向 |
| -------- | ------ | --------- |
| "然后呢？" | 规则不连续，有逻辑空档 | 补充缺失的规则环节 |
| "这怎么算？" | 边界条件未定义 | 补充对应的边界条件 |
| "我为什么要这么做？" | 目标指引不清晰，行动缺乏动机 | 强化胜利条件与行动间的关联 |
| "这不就是猜吗？" | 缺乏信息支撑，沦为运气 | 增加可见信息供玩家推理 |
| "那又怎样？" | 行动结果无关紧要 | 加强行动的影响力或后果 |
| "又要等？" | 等待时间过长，downtime 过高 | 简化回合结构或引入同时行动 |
| "怎么又是我？" | 先手/顺序优势感知明显 | 加入补偿机制或改变顺序方案 |
| "他太强了吧" | 平衡性问题 | 检查数值是否失衡或某个策略是否过强 |
| "这个 token 是干嘛的？" | 组件功能不直观 | 优化组件设计或规则说明 |
| "下一局我不想再来一次了" | 游戏体验不佳 | 最严重的信号，需要大改 |

## 测试记录模板

每次测试后应记录以下内容：

```
游戏名称：[名称]
测试日期：[日期]
参与人数：[人数]
原型版本：v[编号]
测试轮次：第 X 轮

1. 发生了什么？
   [简要描述本局的关键事件]

2. 信号词记录
   - "..." → [对应的规则问题]
   - "..." → [对应的规则问题]

3. 玩家反馈摘录
   - [玩家 A]："..."
   - [玩家 B]："..."

4. 数据记录
   - 游戏时长：[分钟]
   - 分数分布：[各玩家分数]
   - 使用频率：[各行动/策略被选择的次数]

5. 待修改项
   - [ ] [优先级][问题描述]
   - [ ] [优先级][问题描述]

6. 下次测试重点
   - [要特别关注的方向]
```

## 测试阶段的演进

### 第一轮测试

- **谁做**：你 + 1-2 个朋友
- **关注点**：核心循环能否走通、是否有明显逻辑漏洞
- **记录方式**：不做正式记录，关注"卡住"的地方

### 第二轮测试

- **谁做**：你 + 3-4 个玩家（至少包含 1 个非桌游玩家）
- **关注点**：规则是否清晰、数值是否大致合理、游戏时长是否在预期内
- **记录方式**：简单记录信号词和时长

### 第三轮及以后

- **谁做**：你 + 不同组合的玩家（轮换阵容）
- **关注点**：是否有最优解、策略多样性如何、不同玩法是否都可行
- **记录方式**：使用完整记录模板

### 盲测

- **谁做**：完全不认识你的玩家群体（桌游吧/朋友的朋友）
- **关注点**：没有设计师解释的情况下，玩家能否自行游戏
- **条件**：规则书已基本完整、组件已标注清楚

## 测试与修改循环

```
人测试 → 记录问题 → AI 分析问题出修改方案
              ↓
        人评审修改方案
              ↓
    [通过] → 前进或进入精炼阶段
    [不通过] → 修改原型 → 再测试
```

每轮修改原则上只改 1-2 个核心问题。不要一次改太多，否则无法确定哪个修改起了效果。

## 常见测试陷阱

- **为规则辩护**：测试时不解释，不辩护——玩家的困惑本身就是反馈
- **跳过盲测**：你会不自觉地在测试中口头填补规则漏洞，盲测才能暴露这些问题
- **只找桌游玩友测试**：非桌游玩家的反馈同样重要（他们更接近"一般人"的认知水平）
- **不记录**：测试结束后凭记忆修改，很容易遗漏关键细节
- **改太多**：一次修改超过 3 个点，无法判断哪个修改有效
