# 原型构建指南

## 组件管理原则

> **[数据完整性原则]**：所有设计数据只存在于各自的源文档中（规则书、角色、版图、卡牌等设计文档），审查时直接从源文档计算。
>
> 实践中，独立的汇总表会导致数据不同步（曾出现 11 处不一致），评审焦点转而追踪同步问题而非审查设计质量。替代方案：
>
> - 数值审查时直接从源文档重新计算
> - 若需要方法论框架，创建独立的方法论文档（不包含具体数值），审查时根据当前源文档计算
> - 所有设计数据只存在于各源文档中，不复制到其他地方

## 核心理念

- **越丑越好**：不要花时间在美观上，第一版原型用任何能用的材料即可
- **最快可玩**：在你还不确定游戏是否好玩时，花费的时间越少越好
- **以最少组件验证核心问题**：不要一开始就做完整版，只做验证核心循环所需的最少组件

## MVP 版本演进

### v1 — 概念验证原型

**目标**：验证核心循环是否可行，是否有趣。

**规格**：

- 全部使用替代品：索引卡代替卡牌、硬币或棋子代替标记、方格纸代替版图
- 卡牌数量：≤ 20 张（如需要的话）
- 规则：1 页纸，只写核心玩法
- 不做任何美术设计，手写即可

**检验问题**：

- [ ] 核心循环能完整走完吗？
- [ ] 有卡住走不下去的地方吗？
- [ ] 规则中有没有逻辑漏洞？

### v2 — 功能测试原型

**目标**：验证完整游戏流程，检测平衡性。

**升级要点**：

- 补全所有必须的组件（但仍使用替代材料）
- 规则扩展到 3-5 页，覆盖完整流程
- 引入简单的数值/概率表
- 测试至少 3-5 局

**检验问题**：

- [ ] 所有规则项都能执行吗？
- [ ] 数值是否大致平衡？
- [ ] 有没有"最优解"？

### v3 — 盲测原型

**目标**：在没有设计师解释的情况下，其他玩家能否自行上手。

**升级要点**：

- 组件制作尽量清晰（手写+颜色区分即可，不必精修）
- 规则书编写完整（按 rulebook.md 规范）
- 不需要设计师在场解释就能玩

**检验问题**：

- [ ] 首次接触的玩家能不靠解释上手吗？
- [ ] 规则书中是否有某处让玩家困惑？
- [ ] 经 10-15 局测试后，游戏是否仍然有趣？

## 组件推导方法

不要从"有什么组件类型"出发，而是从"需要记录什么信息"出发：

| 需要记录的信息 | 推荐物理组件 |
| --------------- | ------------ |
| 玩家身份/角色差异 | 玩家面板 / 角色卡 / 不同色棋子 |
| 可变数值（生命/金钱/分数） | 轨道 + 标记 / 硬币筹码 |
| 位置/布局 | 版图 / 网格 / 卡牌排列 |
| 私有信息 | 手牌 / 秘密任务卡 |
| 随机性 | 骰子 / 卡牌抽牌 |
| 回合状态 | 起始玩家标记 / 回合计数轨道 |
| 临时状态（某回合生效） | 标记 token / 指示物 |

## 迭代演进标准

- **v1 到 v2**：核心循环可行 → 进入 v2；核心循环有问题 → 回到阶段 ② 修改
- **v2 到 v3**：3-5 局测试后无明显逻辑问题 → 进入 v3
- **v3 到正式**：盲测通过（路人能自行上手）→ 可以进入精炼阶段

## 常见陷阱

- **过度制作**：花大量时间做美术，结果测试发现核心机制不好玩
- **组件过多**：第一版原型组件过多，修改成本极高
- **规则遗漏**：原型中设计师口头填补的漏洞 = 实际游戏时一定会出问题的地方
- **测试不足**：改一条规则后只在脑子里过一遍就认为没问题
