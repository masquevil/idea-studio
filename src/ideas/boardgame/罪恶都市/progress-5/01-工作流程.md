# 罪恶都市 · AI Agent 工作流程（progress-5）

> 本文档为 AI agent 提供完整的、逐步执行的工作流程。
> 每次"推进"执行一个细分任务。
> 阶段③内部遵循「AI 评审 → 用户反馈 → 修改」的迭代循环。

---

## 🚨 核心规则

### 1. 逐任务推进

每次**你（用户）说"推进"**时，AI agent 只执行**一个细分任务**，然后立即停机等待下一次指令。

### 2. 推进完成后停机

每次推进完成后，AI agent 必须使用 `attempt_completion` 工具报告结果并**完全停止**，绝不可自行继续下一轮推进。必须等待用户再次输入"推进"指令后再启动新一轮工作。

### 3. "推进"与"对话"的区分

只有执行细分任务切换时需要说"推进"；用户直接给修改意见时不需要说"推进"。

| 切换 | 是否需要"推进" | 说明 |
| --- | --- | --- |
| ③-A → ③-B | ✅ 推进 | 评审完成后，切换至 PLAN MODE 呈现结果 |
| ③-B → ③-C | ❌ 不需要 | 在 ③-B 中用户直接说话给意见，AI 直接修改 |
| ③-C → ③-A | ✅ 推进 | 修改完成后，进入新一轮评审 |
| ③-C 内多次修改 | ❌ 不需要 | 用户分多次给意见时，直接说话即可，AI 直接修改 |

### 4. 阶段内迭代引擎

阶段③内部遵循以下循环：

```
┌─────────────────────────────────────────────────────┐
│  阶段 ③：MVP 构建与审查                              │
│                                                     │
│  【推进】ACT MODE — 用户说"推进"                     │
│  → ③-A/AI 以资深设计师视角进行五项评审                │
│  → 依次产出 r01→r02→r03→r04→r05 五个文档             │
│  → 停机等待                                         │
│                                                     │
│  【推进】PLAN MODE — 用户手动切换后说"推进"           │
│  → ③-B/AI 呈现评审结果，询问你的反馈意见               │
│  → 你直接说话给出修改方向或确认没问题                  │
│  → 停机等待（你切换回 ACT MODE）                     │
│       ↓（不需要说"推进"，直接说话）                    │
│  【你的反馈 ①】ACT MODE — 你说意见                    │
│  → AI 执行 ③-C 修改                                  │
│  → 停机等待                                         │
│       ↓（不需要说"推进"，直接说话）                    │
│  【你的反馈 ②】ACT MODE — 你说更多意见                │
│  → AI 继续修改                                       │
│  → 停机等待                                         │
│       ↓（任意多次）                                   │
│  【你说"推进"】                                       │
│  → 回到 ③-A 新一轮评审                                │
│       ↓                                              │
│  【循环】③-A→③-B→③-C→③-A→...                      │
│  只有当你说"推进进入阶段④"时                          │
│  → 进入阶段 ④                                        │
└─────────────────────────────────────────────────────┘
```

> **关键点**：③-B/③-C 循环内无论用户分多少次给意见、AI 分多少次修改，都属于同一次循环，不递增推进编号。完整的 A→B→C 才算一轮。

### 5. 🚨 推进 B（用户反馈）必须处于 PLAN MODE

- 执行推进 B 时，AI agent **必须处于 PLAN MODE**
- 如果当前是 ACT MODE，agent 必须：
  1. 提示用户"请切换到 PLAN MODE 以进行用户反馈"
  2. 使用 `attempt_completion` 结束当前推进
  3. 等待用户切换模式后重新"推进"

### 6. 阶段切换由你主动控制

- AI agent **永远不得主动问用户"是否进入下一阶段"**
- 进入下一阶段（如③→④）**完全由用户通过"推进进入阶段④"指令触发**
- AI 完成 ③-C 修改后，应当停机等待，由用户决定是"推进"回到 ③-A 继续循环，还是"推进进入阶段④"切换到新阶段

### 7. 唯一方案

本工作流程仅设计 **draft-5-A** 一个方案。所有产出放在 `draft-5-A/` 目录下。不涉及多方案并行。

### 8. 核心参考文档

| 文档 | 用途 |

| `refs/user-initial-4.md` | v4 原始想法，所有设计的最根本依据。AI 在每个任务的输入中都必须引用，确保设计不偏离方向 |
| `refs/ai-writing-standards.md` | AI 写作规范：设计产出类文档（01~04）必须遵循的结构、格式、措辞准则 |
| `progress-5/04-量化审查规则.md` | 评审工具：⑤项评审（r01~r05）必须遵循的评审行为准则、量化分析方法论和评审标准 |

## 阶段 ③：MVP 构建与审查

> 目标：对继承的规则书、角色、地点、策略牌设计进行系统化审查和迭代修改。
> 前置条件：draft-5-A 的 01~04 文档已就位。`progress-5/04-量化审查规则.md`（审查原则框架）已作为初始化产物创建。
> 设计产物仅 4 个文档（01-规则书初稿 → 02-角色设计 → 03-地点牌设计 → 04-策略牌设计）。
> 评审产出 5 个文档（r01-非量化评审 → r02-量化基准 → r03-设计审查 → r04-综合计算 → r05-修改指令）。

### 推进 ③-A：AI 进行五项评审（r01~r05）

**任务**：AI 以资深桌游设计师视角，依次产出 5 个评审文档。

**前置步骤 — 先理解核心规则**：

> 在开始评审之前，AI 必须先通读规则书全文，确保对游戏的核心机制有正确理解。如果你对任何规则有疑惑或不确认，**必须先向用户提问澄清**，得到确认后再开始正式评审。不要跳过这一步直接开始挑问题。
>
> 具体执行方式（理解核对维度）见 `04-量化审查规则.md` 的**评审行为准则**章节。

**评审规则**：

- 不参考历史评审记录（包括本轮 previous 的 r01~r05），完全基于当前文档内容重新进行一轮完整评审
- 每次评审是独立的，不对比上一轮评审的"问题→落实"关系，而是直接对当前内容做出新的评价
- 评审全程遵循 `progress-5/04-量化审查规则.md` 的评审行为准则、量化分析方法论和评审标准
- 设计产出类文档（如 r02 的计算逻辑）同时遵循 `refs/ai-writing-standards.md` 的写作规范

**输入资料**：

- `draft-5-A/01-规则书初稿.md`
- `draft-5-A/02-角色设计.md`
- `draft-5-A/03-地点牌设计.md`
- `draft-5-A/04-策略牌设计.md`
- `progress-5/04-量化审查规则.md`（评审工具：评审行为准则 + 量化分析方法论 + 评审标准）
- `refs/ai-writing-standards.md`（写作规范：评审产出文档的格式/措辞遵循）
- `refs/user-initial-4.md`（原始想法：确认设计方向不偏离）

**产出文档列表**（在一次推进中依次产出 5 个文档）：

1. **`r01-非量化评审.md`**
   - 覆盖所有非数据的评审内容：
     - 规则书逻辑漏洞、规则矛盾、描述歧义
     - 角色定位合理性、技能设计趣味性、阵营互动频率
     - 策略牌效果平衡性、机制是否有趣
     - 游戏节奏、回合流畅度、上手难度
     - 规则完整性：是否有未覆盖的边界情况（发现时以 FAQ 条目归口到规则书 §11 或规则书正文对应章节，不得要求将边界情况写进技能/效果描述的卡面文字中）

2. **`r02-量化基准.md`**
   - 第一步：检查规则书中各基础操作的投入产出关系是否一致，有矛盾的先修复
   - 第二步：建立 0 特殊能力下的数值基准
     - 分析各阵营/路线的各种策略的资源投入产出比
     - 分析各种策略的执行周期（多少回合完成一次核心操作）
     - 分析理性选择下玩家会优先选择哪些目标
     - 各情景下的预期得分/进度

3. **`r03-设计审查.md`**
   - 根据 r02 的基准检查设计质量：
     - 地图/地点系统：不同区域的资源/收益梯度是否合理
     - 角色/能力：对每个特殊能力的成本收益进行分析
     - 总结能力强度分布（超模 / 合理 / 偏弱）
     - 卡牌/特殊手段系统：效果/成本分析、是否会导致单一策略最优
     - 无基础得分手段的阵营是否有足够补偿

4. **`r04-综合计算.md`**
   - 加入所有特殊能力、环境效果、卡牌效果后的综合结果：
     - 各阵营/路线的综合得分/进度预期
     - 资源循环深度检查：
       - **资源消耗趋势**：有限资源的消耗速度、归零时间点、归零后的游戏状态变化
       - **成本突变检查**：资源耗尽是否导致核心操作成本跳跃性变化
       - **循环完整性检查**：Token/资源从产生→消耗→回收的全链路是否闭环
     - **交叉组合风险**：特殊能力与环境、卡牌的协同是否产生超出预期的效果
     - **策略收敛检查**：是否所有玩家都被迫涌向同一个最优策略
     - **非对称阵营综合对比**：各阵营的综合强度对比
   - 参考 `04-量化审查规则.md` 的深层审查维度进行系统性检查

5. **`r05-修改指令.md`**
   - **最后一个产出**，在 r01~r04 全部完成后汇总生成
   - 作用：给 AI 自己（在 ③-C 修改阶段）用的修改清单，不是给人看的评审报告
   - 格式：极度精简，只包含"改什么"和"为什么改"，无背景分析或方法论引用

   ```
   ## 🔴 必须修改

   1. [文档X §Y.Z] [具体字段] 改为 [新值]
      → 原因：一句话解释

   2. [文档X §Y.Z] 重写 [具体段落]
      → 原因：逻辑矛盾

   ## 🟡 建议修改

   3. [文档X §Y.Z] [建议修改]
      → 原因：潜在风险点

   ## 🟢 可延后

   4. [文档X §Y.Z] [建议]
      → 原因：非关键
   ```

**问题优先级**：

| 优先级 | 含义 | 处理建议 |
| - | - | - |
| 🔴 高 | 设计缺陷——严重影响游戏体验或平衡 | 必须在当前阶段修复 |
| 🟡 中 | 潜在问题——可能导致不平衡或体验不佳 | 建议在当前阶段修复，或标记为测试阶段重点观察 |
| 🟢 低 | 可优化项——不影响核心体验 | 可延后处理，或不处理 |

**产出文档**：无需额外产出。r05-修改指令.md 已在 ③-A 中产出。

### 推进 ③-C：AI 根据反馈修改

**任务**：AI 根据 r05-修改指令.md 和你（在 ③-B 中）的补充反馈，修改对应的设计文档。

**输入资料**：

**产出**：更新 `draft-5-A/` 下的对应设计文档

> 然后进入循环：推进 ③-A → ③-B(PLAN) → [用户直接说话→AI 修改] → 你说"推进"→ ③-A → ...
> 直到你决定进入阶段④。

## 阶段 ④：模拟测试（方法框架）

> 注意：以下仅记录方法框架。执行时再细化具体产出。
> 只有你说"推进进入阶段④"时才进入此阶段。

### 方法概要

1. **AI 开发游戏引擎**：制作《罪恶都市》的 CLI 游戏引擎，支持 JSON 格式的输入/输出
2. **AI 开发并发测试工具**：支持同时运行多个游戏实例
3. **AI agent 模拟**：每个测试实例中，调用 2-7 个 AI agent 模拟人类玩家，通过游戏引擎进行完整对局，记录完整游戏流程
4. **测试后分析**：用 AI 读取每次的游戏流程和结果，检查问题（失衡、无趣选择、死循环等），提供修改建议，记录成文档
5. **循环迭代**：AI 总结修改建议 → 询问你 → 你给意见 → AI 修改设计 → 再次并发测试

**产出**：由你在执行阶段决定具体产出什么文档和格式。

## 任务执行流程（AI agent 每次"推进"时遵循）

### 两文档的作用

| 文档 | 何时读取 | 何时写入 | 内容 |
| ------ | ------ | ------ | ------ |
| `02-进度监控.md` | 推进开始时 | 推进结束后 + 每次 ③-C 修改后 | 简短状态（推进编号、任务、模式、完成日期），帮助 AI 确认当前位置 |
| `03-任务执行记录.md` | 不读取 | 推进结束后 + 每次 ③-C 修改后 | 详细历史（做了什么、产出什么、用户反馈了什么），供日后追溯 |

> **简短性约束（必须遵守）**
>
> - **02-进度监控**：任何行 ≤ 40 字；"当前状态速览"只写 2 行（① 已完成到哪一步；② 下一步做什么）。**禁止**写入反馈详情、修改清单、评审结论。
> - **03-任务执行记录**：每行一句话（≤ 60 字）。③-C 行只写"修改了哪些文档 + 改动类别"。**禁止**逐条列举修改项——细节一律到 r05 修改指令与修改后的设计文档中查。
> - **progress 文档自身的维护（修改 01/02/03/04）不属于"推进任务"**：不得在 02/03 中新增任何记录行。

### 执行步骤

```
0. 读取 refs/user-initial-4.md（如有需要确认方向的情况）

1. 读取 progress-5/02-进度监控.md
   → 确认当前位置（当前完成到哪个推进、下一个任务是什么）

2. 读取 progress-5/00-总览.md
   → 确认项目最新上下文

3. 读取该任务所需的输入资料（设计方案文档等）

4. 执行该任务：
   → 产出对应文档（write_to_file）
   → 产出后对照 04-量化审查规则.md 自查

5. 更新 progress-5/02-进度监控.md
   → 标记该任务为"已完成"
   → 只更新状态和日期，不写详细备注

6. 更新 progress-5/03-任务执行记录.md
   → 记录执行详情（产出了什么文档、修改了什么内容、用户反馈了什么）

7. 使用 attempt_completion 报告完成
   → 🚨 必须完全停止，不可执行任何下一步工作
   → 等待用户下一次"推进"指令
```

### ③-C 修改后的更新规则

③-C 修改针对的是**桌游设计文档**（01~04、r01~r04）的实质性改动。每次修改完成后：

- ✅ 必须更新 `02-进度监控.md`（状态和日期）和 `03-任务执行记录.md`（修改详情）
- ✅ 在 `03-任务执行记录.md` 中以 "—" 行记录本次修改的内容和产出文档
- ❌ **绝不**将"更新 02/03"本身记为一次独立的 ③-C 修改

**示例：**

```
✅ 正确的③-C记录：
  — | 2026-07-31 | ③-C 第1次修改：规则书5条反馈 | ACT | ✅ | 更新 01-规则书初稿.md | ①§1.2游戏目标重写...

❌ 错误的③-C记录：
  — | 2026-07-31 | ③-C 修改：更新进度文档 | ACT | ✅ | 更新 02-进度监控.md 03-任务执行记录.md
  ↑ 对 02/03 的更新是每次修改后的标准步骤，不能作为独立的③-C记录
